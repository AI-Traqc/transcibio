The big picture

What is Transcibio?

Transcibio is an on-device assistant for meetings and notes. You give it audio; it transcribes who said what, lets you ask questions about the conversation, proposes follow-up actions (like drafting an email), and can hold a hands-free spoken conversation with you. The defining rule: every step happens locally — speech recognition, the language model, and the voice all run on your machine. No cloud, no accounts, no data leaving the device.

🎙️

Transcribe

Audio → text with speaker labels ("who said what") and word-level timing.

💬

Chat over it

Ask questions; answers are grounded in the transcript with clickable citations.

⚡

Propose actions

The assistant can suggest structured follow-ups — email drafts, task lists, exports.

🗣️

Talk hands-free

Speak naturally; it listens, thinks, and answers out loud — and you can interrupt it.

Why "local-only" matters

Meetings contain sensitive things — names, decisions, salaries, health, strategy. Most transcription tools ship that audio to a server. Transcibio is built so it physically cannot leak: the AI models live in files on your disk, and the backend talks to them over localhost. That privacy guarantee is the product. Every architectural choice below exists to keep it true while still feeling fast and modern.

Tooling

The tech stack at a glance

Two hand-written halves (a Python backend and a React frontend) wired to a set of optional AI engines. "Optional" is key — if an engine isn't installed, the feature degrades gracefully instead of crashing.

Backend

FastAPI + SQLite · Python 3.10

A web server (FastAPI) that exposes a REST + WebSocket API, plus a single embedded SQLite database file for all data. A background worker thread runs slow jobs (like transcription) off the request path.

Frontend

React 18 + Vite + TypeScript

A single-page app built with Vite, styled with Tailwind and accessible Radix UI primitives. Talks to the backend over REST, Server-Sent Events, and a WebSocket for streaming voice.

The optional AI engines

STT

faster-whisper

Speech → text. Runs locally on CPU or GPU.

Diarization

pyannote.audio

Figures out who is speaking and when.

LLM

Ollama / LM Studio

The "brain" for chat & correction. Reached over localhost.

TTS · DE

Piper

German text → speech, 22.05 kHz, via a subprocess.

TTS · EN

Kokoro

English text → speech, 24 kHz, in-process ONNX.

VAD

Silero (in browser)

Detects when you start & stop speaking, offline.

All six are lazy-imported and faked in tests — so the project installs and runs even with none of them present.

One SQLite file (WAL mode, foreign keys on) holds everything as frozen dataclass records. Transcript edits never overwrite — they create a new revision linked to its parent, giving you a full undo/audit chain.

The design philosophy

Graceful fallbacks everywhere

Transcibio's golden rule: a missing engine should degrade a feature, never break the app. Non-fatal failures are collected as warnings in result objects instead of raised as exceptions. Here's what happens when each optional piece is absent.

When this is missing…What happens instead
pyannote / HF_TOKENSafeDiarizationRunner swallows the failure; the transcript uses "UNKNOWN_SPEAKER" labels and keeps going.
Ollama / LM Studio (the LLM)Chat & correction fall back to RuleBasedChatModelClient — deterministic answers built from the top transcript snippets. Voice mode speaks one rule-based sentence.
A transcript at allChat simply answers as a general assistant — no longer an error.
Piper / Kokoro (TTS)The voice-turn WebSocket returns an error frame; typed text chat is unaffected.
faster-whisper (STT)The voice-command API returns editable fallback text so you can type instead.
FFmpegNative audio still works; only non-native formats (e.g. MP3) need it. Can be made mandatory via TRANSCIBIO_REQUIRE_FFMPEG.
For contributors

Running & testing it

The backend uses uv with a local virtual environment; the frontend uses plain npm. Tests and lint run on every push via GitHub Actions.

Backend

# install (CPU) into the venv
uv pip install --python .venv\Scripts\python.exe ".[dev]"

# run the API server
.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload

# tests & lint
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe -m ruff check

Frontend

# install (postinstall copies offline VAD assets)
npm install

# dev server / production build
npm run dev
npm run build # tsc -b && vite build

# tests
npm run test # Vitest
npm run test:e2e # Playwright

Continuous Integration — .github/workflows/ci.yml

Two jobs run on every push to main and every PR. CI installs only the light dependencies — the multi-GB ML stack is lazy-imported and faked in tests, so the heavy CUDA wheels never download and runs finish in seconds.

Backend job

ruff check → ruff format --check → pytest -q

Frontend job

npm ci → tsc -b (typecheck) → vitest run
